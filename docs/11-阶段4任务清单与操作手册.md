## 4. 推荐实现顺序

1. 先实现纯函数评分规则和测试，避免把业务规则写进 React。
2. 实现文案仓储服务和消息协议，再接管理页。
3. 实现任务与文案关联，确保任务切换不会混用文案。
4. 增加活动记录，所有打开/复制/状态操作从统一服务进入。
5. 扩展笔记列表的排序、筛选、批量状态更新。
6. 最后接侧边栏交互并做完整集成测试。

## 5. 设计约束

- 相关性评分是可解释的本地规则，不调用模型或网络服务。
- 同一笔记在不同任务下必须保存不同评分，使用 `relevanceByTask`。
- `OPEN_NOTE`、`COPY_TEXT` 只记录活动，不改变笔记状态。
- `MARK_PROMOTED`、`MARK_REPLIED`、`MARK_CONTACTED` 只能由用户点击触发。
- 删除文案前必须确认；删除任务不删除笔记。
- 所有业务失败必须返回 `Result` 并在 UI 展示错误，不静默成功。
- 侧边栏只显示当前任务 `copyIds` 里的文案；任务切换后文案选择必须回退到该任务的默认文案。

## 5.1 手工自测步骤（对应 §6「手动」清单）

1. `npm run build`，在 `chrome://extensions` 载入 `dist/`。
2. 管理页 →「文案」：新建文案 A、文案 B。
3. 管理页 →「任务」：任务 1 勾选 A，任务 2 勾选 B，分别保存。
4. 侧边栏选任务 1 → 读取页面 → 每张卡片下方只有 A，点「复制文案」→「已复制文案」。
5. 侧边栏切到任务 2 → 卡片下方文案变成 B（不应出现 A）。
6. 管理页 →「笔记」：切换任务，确认「相关性」列分数随任务变化；用「评分」下拉筛 ≥50 分。
7. 点「打开笔记」和「复制文案」，再到管理页 →「活动」：应各出现一条记录，且笔记状态没变。
8. 把笔记从 `NEW` 一步步推进到 `PROMOTED`；直接跳 `CONTACTED` 应报错并显示红色横幅。
9. 在 `chrome://extensions` 点「重新加载」，再打开管理页：任务、文案、评分、活动都还在。

### 7.3 真实页面验收中发现并已修复的缺陷

**缺陷 A（2026-10-19，实测第 5 步暴露）：打开笔记跳到「扫码登录」或 `error_code=300031 当前笔记暂时无法浏览`。**

三个叠加原因，全部由用户从真实页面右键「复制链接地址」拿到的原始 href 定位：

1. **规范链接丢掉了授权参数。** `canonicalizeNoteUrl()` 为稳定去重丢弃了**全部**查询参数，
   其中包含打开笔记必需的 `xsec_token`。
2. **路径形态假设错误。** 实测搜索卡片链接是 `/search_result/{id}?xsec_token=…`，
   而 `NOTE_PATH_RE` 只认 `/explore/` 与 `/discovery/item/`，导致这类卡片解析不出 noteId、
   整张卡片连同 token 一起被丢弃。同一卡片内还有不带参数的 `/explore/{id}` 链接，
   原先取第一个命中的链接，于是拿到的是没有 token 的那个。
3. **token 被重新编码。** 实测 token 形如 `ABt8…EU0=`，末尾带 `=`（base64 padding）。
   用 `URLSearchParams` 重建 query 会转义成 `%3D`，服务端签名校验失败，正是 `300031` 的来源。

- **修复**：
  - `NOTE_PATH_RE` 增加 `search_result` 分支：三种路径统一解析出同一个 24 位 hex ID。
  - `buildNoteOpenUrl()` 重写：**原样保留页面路径**（不改写成 `/explore/`，否则签名对象变了）、
    按原始片段拼接 query 不做重新编码（保住末尾 `=`）、仅放行 `xsec_token` / `xsec_source` 白名单，
    空值参数丢弃。
  - `findNoteLink()` 改为**优先返回带 `xsec_token` 的链接**，没有才回退到第一个可解析链接。
  - `NoteDraft` / `Note` 新增 `openUrl` 字段；**去重键继续用不含参数的 `canonicalUrl`**，
    因此 token 变化不会造成重复记录。重新读取同一页面时非空 `openUrl` 覆盖旧值（token 会过期）。
  - `note-actions.ts` 新增 `resolveNoteOpenUrl()`：「打开笔记」优先用 `openUrl`，旧数据回退到
    `canonicalUrl`；「复制笔记信息」仍只复制不含 token 的规范链接（避免把 token 粘贴到别处）。
- **验证**：新增 10 个用例。`normalization.test.ts` 8 例，其中一例**逐字复刻用户提供的真实链接**，
  断言输出以 `EU0=` 结尾且不含 `%3D`；`extraction.test.ts` 1 例（fixture 的 token 必须进 openUrl）；
  `note-persistence.test.ts` 1 例（落库保存并在重新读取时刷新 token）。
- **⚠️ 改完必须重载扩展**：`chrome://extensions` 点卡片上的「⟳ 重新加载」，否则浏览器仍在跑旧代码
  （本轮第一次修复无效的直接原因就是没有重载）。
- **⚠️ 旧数据需要重新读取一次**：修复前入库的笔记没有 `openUrl`，打开会回退到不含 token 的链接。
  回到搜索结果页再点一次「读取当前页面笔记」即可补齐。

**缺陷 B（2026-10-19，实测第 6 步时发现）：活动页「任务」列显示原始 UUID。**

- **现象**：活动记录的任务列显示 `7631dbaa-94a1-4365-ad9b-97b12bb6ad05` 这样的内部 ID，用户无法辨认。
- **修复**：`options/pages/activity.tsx` 改为同时加载 `api.taskList(true)`，用 `taskName()` 把
  `taskId` 映射为任务名；任务已删除时显示「（任务已删除）」，不再露出 ID。

**缺陷 C（2026-10-19，实测第 9 步时发现）：批量操作的失败原因可能看不见。**

- **现象**：错误横幅渲染在页面顶部，而「批量标为已审核 / 批量标为不相关」按钮在下方卡片内。
  列表较长时用户看不到失败原因，容易误判为「静默成功」。
- **修复**：`options/pages/notes.tsx` 在批量按钮**同一区域**增加内联错误提示
  （「批量操作未执行：…。整批状态均未改变。」），并把 `bulkStatus` 的异常也纳入 `try/catch`。

**第 9b 步复测提示（重要）**：批量状态机本身是正确的
（`bulkSetNoteStatus` 先整体校验 `canTransition`，任一非法即整批拒绝，`phase4-services.test.ts` 有对应用例）。
用户首次「没有看到报错」的原因是**选中的两条都还是「新发现」**——`新发现 → 已审核` 是合法转移，本就不该报错。
复测必须满足：**一条已推进到「已推广」或之后，另一条仍是「新发现」**，此时批量标为已审核才会被拒绝。

**缺陷 D（2026-10-19，第 9b 步复测发现）：批量被拒时只说「输入内容不合法」。**

- **现象**：复测已能正确弹出红字，但文案是通用的「批量操作未执行：输入内容不合法，请检查后重试。。整批状态均未改变。」
  ——看不出是**哪一条**、**为什么**不能改，末尾还多出一个「。」（消息本身已带句号）。
- **修复**：`bulkSetNoteStatus` 改用 `appErrorWithMessage`，文案点名到具体笔记与当前状态：
  「整批未执行：有 1 条笔记当前状态不允许变更为「已审核」（「…」当前为不相关）。请先取消勾选这些笔记。」
  UI 侧不再拼接前后缀，避免出现「。。」。

**缺陷 E（2026-10-19，第 6 步复测发现）：侧边栏「识别卡片 30 / 提取 0 / 跳过 0」，数字自相矛盾。**

- **现象**：滚动加载后读取，界面显示「识别卡片 30 个 / 成功提取 0 条 / 跳过卡片 0 个」并报
  `NO_VISIBLE_NOTES`（"没有识别到可读取的笔记"）。30 ≠ 0 + 0，用户无法理解。
- **根因**：「识别卡片」取 `signals.noteSections`（实时扫 DOM），而「提取/跳过」来自另一份
  **按页面类型短路**的结果。当时页面停在**笔记详情页**（滚动中打开了笔记，URL 变 `/explore/{id}`），
  详情页不执行批量提取 → 0/0；但详情页是叠加层，底下搜索页的 30 张卡片仍在 DOM 里 → 30。
- **修复**：①「识别卡片」改用 `totalCandidates`，保证恒有 `提取 + 跳过 = 识别`；
  ② 详情页/个人主页改报新错误码 **`NOT_SEARCH_RESULTS`**，文案明确「当前不是搜索结果页…本页不会读取」，
  不再误报"没有笔记"。新增测试锁死该不变式。

**缺陷 F（2026-10-19，第 11 步诊断 JSON 发现）：`durationMs` 恒为 0。**

- **现象**：真实 JSON 里 `"durationMs": 0` 且 `startedAt === finishedAt`（都是 `03:44:42.725Z`）。
- **根因**：计时起点在 `buildDiagnostics()` 内部才取，而那时扫描已经结束，前后同一瞬间。
- **修复**：`createXiaohongshuAdapter` 在扫描前后各记一次时间并传入 `buildDiagnostics`，
  `durationMs` 由两端时间差算出。

**缺陷 G（2026-10-19，第 7 步复测发现）：非小红书页报「无法访问当前页面」，误导用户。**

- **现象**：在 `www.baidu.com` 点读取，红字为「无法访问当前页面。请在目标页面上重新点击扩展图标，然后再试。」
  ——**没有静默返回空列表**（硬性要求已满足），但暗示是用户操作有误。
- **根因**：`host_permissions` 只含 `xiaohongshu.com`，其它站点 `tab.url` 不可读，代码走进了
  「地址拿不到 → `PERMISSION_DENIED`」分支。
- **修复**：该分支改判 `UNSUPPORTED_PAGE`，文案说明「最常见的原因是当前标签页不是小红书」。
