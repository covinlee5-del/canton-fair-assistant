**要做的事**

### T5.3 统计聚合服务（1 天）

**目标**：把聚合逻辑写成纯业务服务，**不写在 React 组件里**（`AGENTS.md` §3）。

**新建**：`src/services/stats-service.ts`

**输入**：`NoteRepository`、`TaskRepository`、`ActivityRepository`

**输出**（建议结构，字段名可调整但要一次定死）：

```ts
export interface TaskStats {
  taskId: ID;
  taskName: string;
  totalNotes: number;        // 关联到该任务的笔记数
  highRelevance: number;     // relevance.level === 'high'
  mediumRelevance: number;
  processed: number;         // status !== NEW 的数量
  promoted: number;          // status 为 PROMOTED / REPLIED / CONTACTED
  replied: number;           // status 为 REPLIED / CONTACTED
  contacted: number;         // status === CONTACTED
  irrelevant: number;
  withReplyText: number;     // 有 userComment 的跟进记录数
}
export interface OverallStats { byTask: TaskStats[]; totals: Omit<TaskStats,'taskId'|'taskName'>; generatedAt: ISODate; }
```

**关键约束**

1. **只统计已记录的数据**。不要算转化率、曝光量。若要给百分比，只允许给「已处理占比 = processed / totalNotes」这种**分子分母都在库里**的比值，且 UI 要标注口径。
2. 笔记与任务是**多对多**：`Note.taskIds` 是数组，`relevanceByTask` 按任务存分。统计必须按任务分组，不能简单地"一条笔记算一次"。
3. `status === IRRELEVANT` 的笔记要单独计数，不要混进「已处理」的解释里——UI 上说明清楚。

**验收**

- 新增单元测试至少覆盖：空库、单任务、多任务、一条笔记关联两个任务、全状态分布。
- 纯函数优先，便于测试（不要把 `Date.now()` 直接写在聚合里，从参数传 `now`）。

### T5.5 导出（0.5 天）

**目标**：用户点一下，下载一个 JSON 备份文件。

**新建**：`src/services/backup-service.ts`

**格式**：严格按 `src/shared/types/export.ts` 与 `docs/03` §9，不要改结构：

```ts
{ format: 'canton-fair-assistant-backup', schemaVersion: 1, exportedAt, appVersion, data: { tasks, notes, copies, activities, settings } }
```

**⚠️ 必做：剥离 `xsec_token`**

`Note.openUrl` 里存着带 `xsec_token` 的完整链接。**导出文件是会被用户分享、发到群里、上传网盘的**——不剥离等于泄露用户自己的会话签名。

```ts
// 导出时对每条 note 做一次净化
const safeNote = { ...note, openUrl: null };  // 或剥离 query 后的纯 canonicalUrl
```

实现后必须写测试断言：导出 JSON 字符串里**不出现** `xsec_token`、不出现 `%3D`（token 编码残留）。

**其它要求**

1. 只由用户点击触发（红线第 5 条），不许自动导出、不许定时导出。
2. 文件名：`canton-fair-assistant-backup-YYYY-MM-DD-HHmm.json`
3. 导出成功后更新 `Settings.backup.lastExportAt`。
4. 数据量大时（笔记 > 5000）要提示耗时，不要卡死界面。

**验收**

- 导出文件能被 `JSON.parse`，顶层 `format`/`schemaVersion` 正确。
- 断言不含 `xsec_token`。
- 导出的 `notes.length` 与「笔记」页「全部任务」下的条数一致。

### T5.6 导入（1 天）

**新建**：`src/shared/domain/validation.ts`（`docs/03` §10 已经点名要这个文件，但至今不存在）

**格式校验**（任一失败 → 整体拒绝，返回 `ErrorCode.IMPORT_INVALID`）

1. `format === 'canton-fair-assistant-backup'`
2. `schemaVersion` 落在支持范围（当前只支持 `1`）
3. 五个数组字段类型正确、`id` 唯一、必填字段非空
4. 引用完整性：`note.taskIds` 里的任务、`activity.noteId` 的笔记、`task.copyIds` 的文案，是否存在
5. 枚举值合法（`NoteStatus`、`TaskStatus`、`ActivityAction`、`TaskCategory`）

**冲突合并**：按 `docs/03` §11 的既定策略 —— **按 `id` 合并，字段冲突以 `updatedAt` 较新者为准**，并生成导入报告（新增 / 更新 / 跳过 / 冲突条数）。不要自己发明策略。

**事务语义**：先全量校验通过，再写入。**校验失败时一条都不写**，原有数据不受影响。

**⚠️ 两个后端不一致的问题（必须显式处理）**

| 数据 | 存储位置 |
|---|---|
| tasks / notes / copies / activities | IndexedDB（4 个 store） |
| settings | `chrome.storage.local` |

IndexedDB 可以用一个事务包住四个 store，`chrome.storage.local` 不在同一事务里。**这是本阶段唯一真正棘手的架构问题**，必须在开工前定方案。建议：

> 先写 IndexedDB（单事务，失败即整体回滚），成功后再写 settings；若 settings 写入失败，返回 `STORAGE_ERROR` 并明确告知「业务数据已导入，设置未更新」，让用户重试导入设置部分。**把这条写进 `docs/03` §11，不要口头约定。**

**验收**

- 至少 4 个用例：正常导入、`format` 不符、`schemaVersion` 过高、引用完整性失败。
- 每个失败用例都要断言**原有数据未被修改**。
- 导入自己刚导出的文件应当成功且不产生重复。

## 6. 红线与风险

### 6.1 红线（违反即停止）

1. 导出**必须**剥离 `xsec_token`（这是隐私泄露，不是"优化项"）。
2. 不自动导出、不自动上传、不做默认开启的云端备份。
3. 不抓取私信/评论，跟进内容只能用户手抄。
4. 不推算未记录的曝光/转化指标。
5. 导入失败必须整体拒绝，绝不允许部分写入。

### 6.2 已知风险

| 风险 | 影响 | 对策 |
|---|---|---|
| 两个存储后端（IDB + chrome.storage）无法原子写入 | 导入可能"业务数据成功、设置失败" | T5.6 的显式方案 + 文档记录 |
| 笔记与任务多对多 | 统计易重复计数 | T5.3 按 `taskIds` 分组，测试覆盖"一条笔记两个任务" |
| 列表数据量大 | 笔记页/统计页卡顿 | 用 `uiPrefs.pageSize` 分页；统计在服务层聚合，不渲染全量 |
| `xsec_token` 出现在别处 | 导出泄露 | 导出前统一过一次净化函数，并加断言测试 |
